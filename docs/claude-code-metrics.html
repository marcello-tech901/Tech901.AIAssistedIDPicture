Architecture & Planning
Architecture
Come up with an implementation plan for PRD-new.md. This is a .NET WPF kiosk application for capturing ID photos of adult training cohort participants. Never use K-12 language. Azure resources should be provisioned programmatically via Bicep. Include teardown scripts. Use CommunityToolkit.Mvvm, Generic Host DI, and a ViewModel-first navigation pattern.
Why it works: Sets constraints upfront — language rules, tech stack, infrastructure-as-code — giving the LLM precise boundaries instead of a vague "build me an app." This single prompt shaped the entire project architecture.
Architecture
[12,673-char implementation plan] Complete solution skeleton: 4-project dependency graph (App → ViewModels → Core, App → Infrastructure → Core), state machine transitions, DI registrations, Azure Bicep modules, config layering (appsettings.json → User Secrets → env vars), and publish profile — all specified before writing a single line of code.
Why it works: Front-loading a comprehensive plan means the LLM produces coherent, consistent code across dozens of files instead of ad-hoc fragments that conflict. The dependency graph prevents circular references from day one.
Infrastructure
The Azure DI registration is broken. Speech and Face services always resolve to null fallbacks. I've verified User Secrets are populated correctly via `dotnet user-secrets list`. The issue is that config checks run at registration time (in AddInfrastructure), before the Generic Host has finished building — so IConfiguration isn't fully layered yet. Switch to resolution-time factory lambdas.
Why it works: Provides root cause analysis with evidence (User Secrets verified), identifies the timing issue (registration vs. resolution), and proposes the exact pattern to use. The LLM doesn't waste tokens on diagnosis.
Debugging & Problem Solving
Debugging
The face detection positioning always says "move back" regardless of distance. The webcam preview is also not mirrored. Root cause: Azure Face API returns landmark coordinates as normalized 0–1 floats, but our PositioningViewModel treats them as pixel values. The math comparing face-width-to-frame-width ratio is off by orders of magnitude. Also flip the preview with ScaleTransform.
Why it works: Pinpoints the exact mismatch (normalized vs. pixel coordinates), explains the downstream symptom, and bundles a related UX fix. Two bugs, one coherent prompt, zero ambiguity.
Debugging
None of our speech-to-text functionality seems to be engaged. When the user reaches name capture, they should hear a TTS prompt, then the mic opens for STT. Expected: "Please say your name" → mic on → recognition → display result. Observed: silence, no mic activation. The SpeechConfig is created in the constructor but RecognizeOnceAsync is never called from NameCaptureViewModel.
Why it works: Follows the "Expected / Observed / Evidence" pattern. Narrows the scope from "speech doesn't work" to a specific missing method call in a specific ViewModel — saving multiple rounds of investigation.
Debugging
Webcam capture quality is poor. Three separate issues: (1) OpenCvSharp defaults to 640×480 — we need to request 1920×1080 from the device. (2) The capture path round-trips through JPEG twice (once in WebcamService, once in ImageProcessingService) — keep the raw Mat until final export. (3) The preview and capture share the same frame grab — add a separate high-res capture path.
Why it works: Decomposes a vague "quality is bad" complaint into three distinct, fixable layers. Each problem has a clear cause and proposed solution. The LLM can tackle them independently.
Iterative Refinement
Iterative Refinement
The TTS-to-mic transition has a noticeable delay. Two causes: (1) 500ms hardcoded Task.Delay between TTS completion and STT start — reduce to 100ms. (2) SpeechRecognizer is created fresh each time — pre-warm it in the constructor so the first call doesn't pay the SDK initialization cost. Keep the existing CancellationToken pattern.
Why it works: Identifies two independent latency sources with specific fixes. The "keep the existing pattern" note prevents the LLM from over-refactoring working code while fixing the performance issue.

Code Review & Documentation
Code Review
Review the codebase for: (1) async/await correctness — are we blocking the UI thread anywhere? (2) Lock contention — is the RosterService lock too coarse? (3) Azure SDK efficiency — are we disposing SpeechRecognizer correctly? (4) UX responsiveness — any operations that should show a loading state but don't?
Why it works: Instead of "review my code," specifies four precise review axes. Each maps to a real failure mode (UI freeze, deadlock, resource leak, perceived lag). The LLM delivers structured findings instead of generic observations.

06 10 Patterns That Worked
Plan Before You Prompt
The most productive sessions started with a comprehensive implementation plan — dependency graphs, file lists, state machines — before any code was generated. Front-loading architecture prevents rework.
Specify Constraints, Not Steps
Telling the LLM "never use K-12 language" or "use resolution-time factory lambdas" produces better code than step-by-step instructions. Constraints let the LLM find the optimal path within boundaries.
Expected / Observed / Evidence
Bug reports that include what should happen, what does happen, and proof (log excerpts, User Secrets verification) eliminate diagnostic roundtrips. One prompt instead of five.
Decompose Quality Issues
"Quality is bad" becomes three fixable layers: resolution defaults, double compression, shared capture path. Breaking vague complaints into specific causes lets the LLM tackle each independently.
Read Before Write
Asking "what does the current implementation look like?" before requesting changes prevents solutions built on wrong assumptions. This saved entire sessions of rework.
Scoped Review Axes
Instead of "review my code," specify dimensions: async correctness, lock contention, resource disposal, UX responsiveness. Each axis maps to a real failure mode and yields actionable findings.
Guard Rails on Polish Passes
"Fix the UI but don't break functionality" scopes visual work without over-constraining solutions. Give concrete examples to anchor the search, then let the LLM find additional issues.
Bundle Related Fixes
The best prompts addressed 2–3 related issues in one coherent request — like fixing normalized-vs-pixel coordinates AND mirroring the preview. Grouping related changes reduces context-switching overhead.
Preserve What Works
"Keep the existing CancellationToken pattern" prevents the LLM from over-refactoring while fixing a specific issue. Explicitly protect working patterns when requesting targeted changes.
Meta-Prompt for Future Sessions
Using the LLM to create CLAUDE.md — context for future LLM sessions — compounds productivity. Each session starts faster because project-specific knowledge is pre-loaded.
